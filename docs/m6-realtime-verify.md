# M6 实时验证（Real-time Inference Verification）

> 目的：拿一个**已训练好的模型**，对着**摄像头 / 图片 / 视频**跑推理，把识别结果**画出来给人看**。
> 它回答的问题是「这个模型在这个场景下到底认出了什么」，而不是「mAP 是多少」。

---

## 一、定位与边界（先说清不做什么）

### 与现有模块的区别

| 模块 | 做什么 | 有无真值 | 产出 |
|---|---|---|---|
| M3 评估 | `model.val()` 在静态数据集上算 mAP / 混淆矩阵 | **有**（数据集带标注） | 指标数字 |
| M4 部署导出 | 把 `.pt` 转成 ONNX / TorchScript 等格式 | 无 | 格式文件 + 哈希 |
| **M6 实时验证** | 摄像头 / 图片 / 视频 → 推理 → 叠加显示 | **无** | 屏幕上的框（MVP 不落盘） |

**这不是第二个评估模块**：评估是「有真值、算指标」，M6 是「无真值、肉眼看」。

### MVP 明确不做

- **不落盘**：不保存截图、不建任务状态机、不写 `storage/`。实时看即可。
  （「保存这次验证」留作后续任务，等真有需求再加。）
- **不做多模型对比**：那是 M3-04 的职责。
- **不修改任何原始文件**：与清洗/规范化同一条原则。

### 与 M7 预标注的关系

M6 与 M7（模型批量预标注）**共用同一个推理后端抽象**。M6 是单帧 / 流式，
M7 是批量。所以 M6 的 `core/infer/` 是后续 M7 的地基，设计时就按这个前提做。

## 二、架构：画面怎么传

### 方案 A（采用）：浏览器抓帧 → 后端推理

```
浏览器 getUserMedia 打开摄像头
   │  每帧画到 canvas → toBlob(JPEG, quality)
   ▼
WebSocket 二进制帧  ──────────────────►  后端
                                          │  推理（ultralytics，子进程）
                                          ▼
浏览器叠加框  ◄──────────────────────  返回 JSON：框 + 类别 + 置信度
```

**为什么不用后端直连摄像头（cv2.VideoCapture）**：

- 后端一旦部署到服务器 / 容器就没有摄像头了，模块会**只能在特定机器上用**；
- `cv2.VideoCapture` 在 Windows 上对部分摄像头的打开/释放很挑，容易卡死；
- 方案 A 的摄像头权限、设备选择由浏览器负责，后端**不需要 `opencv`**。

**为什么不用前端推理（onnxruntime-web / TF.js）**：

- 违背「数据管道逻辑全在 core」的硬约束；
- 依赖先导出 ONNX，且要在浏览器里重建预处理/后处理，容易与训练时不一致。

### 关键设计：推理在**子进程**里

API 进程**不加载 torch/ultralytics**（沿用 M2/M3/M4 的隔离原则）。
推理进程是一个常驻子进程，通过 stdin/stdout 的行协议（JSON Lines）收发：

```
主进程（API）                         推理子进程
   │  {"type":"load","weights":...,"classes":[...]}   │
   │ ───────────────────────────────────────────────► │
   │  {"ok":true,"task":"detect","classes":[...]}     │
   │ ◄─────────────────────────────────────────────── │
   │  {"type":"frame","id":7,"jpeg":"<base64>"}       │
   │ ───────────────────────────────────────────────► │
   │  {"id":7,"detections":[...],"ms":42.1}           │
   │ ◄─────────────────────────────────────────────── │
   │  {"type":"close"}                                │
```

- **常驻而不每帧起进程**：起进程要几秒（import torch），每帧起一次不可用。
- **行协议而不是自定义二进制**：便于 debug，出问题能直接看日志。
- 帧用 **base64 传 JPEG**：与 WebSocket 文本帧兼容，协议简单；
  每帧约几十 KB，本机 / 局域网完全够用。

> 实测性能目标：CPU 上 imgsz=640 单帧推理约 30~150ms（取决于模型与机器），
> 因此**帧率预期 3~15 FPS**。MVP 接受这个水平——「验证识别情况」够用，
> 不追求流畅视频。前端做**丢帧策略**（上一帧没回来就跳过），避免堆积延迟。

## 三、支持的权重格式（能力探测，不写死）

沿用 M4 的做法（`core/deploy/formats.py`）：**`find_spec` 探测，不 import 重依赖**。

| 格式 | 推理所需 | 本机现状 | 说明 |
|---|---|---|---|
| `.pt` | torch + ultralytics | ✅ 已装 | 主路径，必支持 |
| `.onnx` | **onnxruntime** | 待装（本次一并安装并验证） | ultralytics 走 onnxruntime |
| `.torchscript` | torch | ✅ 已装 | 可用 |
| OpenVINO / Engine / TFLite / CoreML | 各自运行时 | ❌ 未装 | 探测后如实报「缺什么」，不启动注定失败的推理 |

**ONNX 的类别来源**：ONNX 文件**不带 `data.yaml`**，类名必须显式提供。
优先级：请求里显式给的 `classes` > 同目录 / 模型卡里的 `data.yaml` > 报错要求填写。

**不乐观假设可用**（README 设计决策 13）：界面列出格式时同时给 `available` 与 `reason`，
不可用的格式**在启动推理前就拒绝**，而不是让用户选完等到失败。

## 四、core 结构（拟）

```
core/infer/
├── formats.py       权重格式清单 + 能力探测（find_spec；与 deploy/formats.py 同风格）
├── spec.py          InferSpec：权重 / 类名 / 设备 / imgsz / conf / iou（参数契约）
├── worker.py        常驻推理子进程：stdin/stdout JSON Lines 协议
├── session.py       主进程侧：子进程生命周期、请求-响应配对、超时、优雅退出
├── ultralytics_infer.py   真正的推理实现（唯一 import ultralytics/torch 处）
└── result.py        Detection 结构 + 归一化（纯函数，便于测试）
```

设计要点：

- **`result.py` 是纯函数**，可单测，不依赖 torch（与 `eval/result.py` 同理）。
- **`ultralytics_infer.py` 只在子进程里被 import**。
- 推理结果坐标用**绝对像素 xyxy**（与 IR 一致），前端负责缩放叠加；
  这样 M7 复用同一结果进 IR 时不需要二次换算（README 设计决策 7：只在出口归一化一次）。
- 分类模型（`task=classify`）返回整图类别 + 置信度，无框；前端用标签展示。
  这样 M6 对 DMD 这类分类模型也能用。

## 五、API（拟）

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/infer/formats` | 支持的权重格式 + 本机可用性 + 缺失原因 |
| GET | `/api/infer/weights` | 可选权重来源（模型库里已注册的 + 允许手填外部路径） |
| POST | `/api/infer/models` | 加载权重并校验（返回 task / 类名 / 是否成功） |
| POST | `/api/infer/image` | 单张图片推理（上传或给路径），返回检测结果 |
| WS | `/api/infer/ws` | 实时流：收帧 → 回结果 |

WS 沿用现有模式（`app/api/routes/train.py` 的 `call_soon_threadsafe` 投递），
但注意：**这里是双向高频**，与训练那种「服务端单向推」不同，
需要处理背压（客户端帧发太快时服务端丢弃旧帧而不是排队）。

## 六、前端（拟）

- 路由 `/verify`（菜单挂在「模型库」下或单独一项，待定）
- 页面 `VerifyCenter.tsx`：
  - 权重选择（模型库下拉 + 外部路径输入）
  - 参数：`conf` / `iou` / `imgsz` / 设备
  - 输入源切换：摄像头 / 图片 / 视频
  - 画布叠加显示（复用 `SampleGrid` 的配色约定：**同一类别颜色一致**）
  - 实时 FPS 与单帧耗时显示
- **摄像头无权限 / 无设备时**给出明确提示（不是静默失败）
- 无 GPU 时如实显示「CPU 推理」——本机就是 CPU

## 七、验证方式（不许「应该可以」）

1. **单元**：`result.py` 的归一化纯函数测试（坐标、类别、空结果、分类任务）。
2. **协议**：`worker` 的行协议测试（用假推理后端，不依赖 torch）。
3. **真实图片推理**：用 `storage/demo_sources/tiny_det` 的图 + `smoke_yolo11n/weights/best.pt`
   （12 图冒烟模型，mAP 0 属正常，见 HANDOFF）真实跑一次，确认返回结构正确。
4. **真实 ONNX 推理**：装上 `onnxruntime` 后，用 M4 导出的 ONNX 真跑一次
   （同时**正面验证 M4 的 ONNX 导出是否可用**，此前因缺包从未真实跑过）。
5. **真实摄像头**：本机有摄像头，前端交互需在浏览器里实际打开验证（R-33 的教训：
   不能只靠 `tsc + vite build`）。
6. **无设备降级**：摄像头不可用时确认提示正确、不崩溃。

## 八、风险与决策

| # | 事项 | 决策 / 说明 |
|---|---|---|
| M6-R1 | 帧率上不去 | 接受 3~15 FPS；丢帧策略防堆积。要流畅视频需换方案（前端推理或 WebRTC），代价大，暂不做 |
| M6-R2 | ONNX 类别缺失 | 必须显式提供类名；界面给输入框，缺类名直接报错而不是猜 |
| M6-R3 | 推理结果是不是「标注」 | **不是**，是**显示**。M6 不产出数据集；伪标注是 M7 的事，且必须人工复核 |
| M6-R4 | 摄像头隐私 | 画面只在本机浏览器与后端进程间流转，**不落盘、不外传**；MVP 无任何截图保存 |
| M6-R5 | 与 M4 格式清单的关系 | 两份清单侧重不同（M4 管「能不能导出」，M6 管「能不能推理」），**不强行合并**，但都走 `find_spec` 探测 |
| M6-R6 | 子进程卡死 | 请求带超时；超时则重启推理子进程，不影响 API 进程 |
